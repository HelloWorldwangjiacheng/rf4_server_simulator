## Problem Statement

路亚玩家中鱼后立刻秒脱钩（f0=1/f0=2, hooked=true）：同一会话路亚竿真脱钩 43 次、底钓竿
0 次；脱钩间隔呈双峰（0.05~0.95s / 0.5~2.0s），精确命中客户端脱钩判定器"保持力 ×0.05"
分支的两个签名窗口。用户实测手持竿做动作时上鱼同样秒脱——判定输入与玩家操作无关。

根因（归因分析见 [docs/路亚秒脱钩归因分析-2026-11-12.md](../../../docs/路亚秒脱钩归因分析-2026-11-12.md)）：
客户端搏鱼态进入时一次性读取"钩组实例/玩法分类/作钓活跃"三个本地挂载态并锁定整场，
而服务端搏鱼期 4/22 里全部挂装组件的 flags 都是定义基值裸值、拟饵树完全缺席。官方路亚
抓包（lure2 19 帧）证实搏鱼期每 2s 全树帧中所有挂装组件 flags = 定义基值 | 运行位
（拟饵/钩 +1024，竿/轮/线/前导 +1024|2048，轮零件 +1024），且拟饵树（ioombppcnlh+双钩）
每帧都在。组件不在搏鱼挂载态 → 客户端路亚钩组实例构造/玩法判定翻车 → 保持力 ×0.05 →
秒脱。底钓竿架类走无条件全值分支不依赖组件挂载态，故底钓零脱钩。

先例：PR #387 已验证"缺 1024 挂竿位时客户端钩实体不进搏鱼态"。本次把同一运行位族补齐到
搏鱼期全部组件，并补上拟饵树。

## Solution

搏鱼期间客户端收到的 4/22 与官方一致：每 2s 的装备快照里竿、轮、主线、前导、拟饵、钩全部
带挂载运行位，路亚拟饵树（拟饵本体+内置钩）每帧都在；路亚中鱼钩帧是拟饵容器形状（拟饵
本体+钩，官方 429B 同构）而非裸钩。玩家侧表现为路亚中鱼后能正常搏鱼，秒脱簇消失。

## User Stories

1. 作为路亚玩家，我中鱼后不再秒脱钩，可以正常收线搏鱼把鱼拉上来。
2. 作为路亚玩家，我中鱼时看到拟饵/钩进入搏鱼态（与底钓中鱼演出同等存在感）。
3. 边界：底钓/浮钓/海钓的搏鱼期推送行为不回归——底钓无拟饵树（官方底钓搏鱼帧本就无拟饵），
   浮钓/海钓按各自挂装物自适应。
4. 边界：不改脱钩结算链（14/12 处理、磨损账、escapes 计数、跑鱼播报均不动）。
5. 边界：17/9 断件恢复路径的装备树重建不注入运行位（官方断件帧形状未采样，保持现状）。

## Implementation Decisions

- 模块：`internal/gameserver`
  - 新增 `fight_mount_bits.go`：
    - `markFightMounted(v *proto.Value, catOf func(numericID int64) (int64, bool))`——
      递归遍历树，按每层对象的 `iofbjlaadfg`（定义下标）查 cat，按上表注入
      `hgaijieklek |= 增量`；无 iofbj 字段的对象跳过。定位复用 `fieldIdxByCS`。
    - cat 查询走现有 item_def 定义缓存/批量 IN 查询，禁止每对象单查（push 每 2s 热路径）。
    - 增量表为包级常量 map（cat → bits），与 Evidence 表一致。
  - `profilebuild.go`：
    - 新增 `Push4_22FightSync(gear string, extraGUIDs []string)`：按调用方给定的竿
      buildFightItemsForGear(full=true)（竿+槽11线，不触碰钓鱼状态、无 resume 副作用）
      + 拟饵树（该竿 `mountedLureGUID` 非空时 `ItemToTree(lureRow)` 整树追加）
      + extras（轮/竿/前导，复用现有附加逻辑）→ 批量查品类（失败重试一次，
      仍失败告警并放弃本帧，绝不静默发裸基值树）→ `markFightMounted` 全量注入 → 推送。
      仅路亚有拟饵树；底钓无拟饵自然不追加（与官方底钓帧无拟饵树一致）。
    - 调用点一：**14/11 中鱼确认**（hFishingHooked，钩帧之后）——客户端搏鱼 ctor
      一次性锁定挂载态，竿/线/轮/前导的运行位必须当刻可达；extras 取受力链
      （rigGearIDs 的轮/前导/铅芯/丝锁）。调用点二：`reel_fight_wear.go` 磨损结算，
      gear = 本次结算竿 `w.rodGUID`（多竿场景非手持竿）。17/9 的
      `Push4_22Items` 调用点（protocol_dynamic_handlers.go:399）保持不变。
    - `markHookMounted` 扩展：`ioombppcnlh`（拟饵容器本体）同钩规则 `|= 1024`
      （官方拟饵本体 22016；现只标 `agedjipcnpe`）。
  - `serverdb.go` `buildMountedHookTree`：当钩行归属拟饵（`mountedLureGUID` 非空且钩为
    拟饵内置，按现有 bait_hook/rig_component 归属判断）→ 返回**拟饵整树**并标挂位；
    独立钩行（海钓串钩单钩等）保持裸钩形状不变。
  - 拆出 `mountedHookSubTree`（原单钩树语义：钩行优先、出厂钩从拟饵树摘单钩），
    供 `mountedHookDef` 钩物理/强度链路继续读钩本体定义；不做 tunable 热关开关，
    线上异常按既有流程回滚二进制。
- 与 [hook-mounted-flag-all-rigs](../hook-mounted-flag-all-rigs/spec.md) 的关系：该 spec
  的"中鱼钩帧 flags=22016 全钓法"已落地（handlers_game.go:1366/1369 mounted=true + 递归
  markHookMounted），本 spec 不重复；其"串钩组/拟饵 rig=ioombppcnlh 嵌套容器"形状目标由
  本 spec 的 buildMountedHookTree 改造完成。
- 协议面不变：4/22 的 args 结构（`S("61")` + 树）与 14/12/14/11 全部不动，只改树内容
  （flags 字段值、新增拟饵树元素）。

## Testing Decisions

- 单测（`fight_mount_bits_test.go`）：
  - 增量表逐 cat 断言：构造带 `iofbjlaadfg` 的假树（用 8.5.2 基值），注入后 flags 与
    官方观测值逐项相等；cat34/无 iofbj 对象不变。
  - `markHookMounted` 扩展：拟饵容器本体 + 嵌套双钩全部补 1024。
- 单测（`profilebuild_test.go` / 既有 Hook/Fight 测试扩展）：
  - 路亚搏鱼期推送含拟饵树（ioombppcnlh 顶层、钩带 1024）且竿/线/轮 flags 带运行位。
  - 底钓搏鱼期推送不含拟饵树（回归保护）。
  - 路亚中鱼钩帧顶层 = ioombppcnlh；海钓单钩场景保持裸钩（回归保护）。
  - **14/11 调用点集成测试**：走 hFishingHooked，断言中鱼确认当刻收到两帧 4/22
    （先钩帧、后全树运行位同步），而非只直调 Push4_22FightSync。
- 全量 `go test ./...`（既有基线失败 TestCafeNativeFlowPaysAndPushesRemoval 不计）。
- 实机验收：用户路亚连竿实测——预期中鱼后可正常搏鱼起鱼，秒脱簇（<2.5s 真脱钩）大幅
  下降；同时观察底钓无回归、断件后装备树重建正常。（PR #452 评审后实装 14/11 当刻
  全树同步；实机确认中鱼后"立即"收到该帧，而非收竿/脱钩后。）
